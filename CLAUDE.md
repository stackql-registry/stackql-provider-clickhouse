# CLAUDE.md

## Project

This repository builds and documents the `clickhouse` provider for [StackQL](https://github.com/stackql/stackql), enabling SQL-based query and provisioning operations against the ClickHouse Cloud API - organizations, services (lifecycle, scaling, settings, passwords), API keys, members and invitations, backups and backup configuration, private endpoints, BYOC infrastructure, usage cost, activities/audit, the ClickStack surface (dashboards, alerts, sources, webhooks), and Managed Postgres services.

**Scope: ClickHouse Cloud control plane only.** The ClickHouse server HTTP interface (SQL-over-HTTP on any self-managed or Cloud service endpoint, plus typed resources introspected from `system.*` tables) is a distinct surface with disjoint auth, and is reserved as the future sibling provider `clickhouse_server` - the databricks_account/databricks_workspace split precedent. Record this in the README as roadmap, including the design sketch: a statements resource per the snowflake sqlapi precedent, and system-table resources generated by introspecting `system.columns` per the gitlab/newrelic introspection precedent.

The provider is built using the `@stackql/provider-utils` package and follows the repository pattern established in [`stackql-registry/stackql-provider-k8s`](https://github.com/stackql-registry/stackql-provider-k8s/tree/feature/provider-dev) (branch `feature/provider-dev`). When in doubt about structure, scripts, testing, or docs, that repository is the reference implementation - mirror it. Sibling-build NOTES.md findings are reused, not re-derived - in particular the jira basic-auth construct finding.

## Positioning context

ClickHouse maintains two official Terraform providers (the Cloud infrastructure provider and the DBops provider for database-level objects) with separate release trains and alpha/stable channels. There is no maintenance ambush here - the angle is unification: what requires two Terraform providers is two SQL namespaces in one StackQL session once `clickhouse_server` lands, and the Cloud provider alone leads with FinOps (the usage-cost resources) and estate inventory. The comparison is expressed through capability statements and runnable examples, never editorializing.

## Spec source

The ClickHouse Cloud API serves its own OpenAPI spec as JSON at the API base, `https://api.clickhouse.cloud/v1` (unauthenticated). ClickHouse has publicly committed to spec quality for tooling consumers (named types over inline schemas, correct integer types, structured validation errors). `bin/fetch-spec.sh` downloads it into `provider-dev/downloaded/`, validates with `@apidevtools/swagger-parser`, and records date and content hash in `provider-dev/config/spec_pin.json`; refreshes are reviewed diffs, never silent regenerations. Note the vendor's own caveat that the API evolves and consumers may need to adjust - the pin-and-diff discipline is the answer.

Beta-flagged endpoints (e.g. `clickhouseSettings`, marked with contract-may-change disclaimers) are mapped normally but tagged in the inventory and surfaced as beta in the docs, mirroring the vendor's labelling.

## Design principles

- **Fixed server, basic auth** - the base URL is the literal `https://api.clickhouse.cloud`; no server variables, so the dotted-host router constraint does not apply. Auth is HTTP Basic with the API key pair (Key ID as username, Key Secret as password) - reuse the jira basic-auth construct finding to settle the env var convention (`CLICKHOUSE_CLOUD_KEY_ID` / `CLICKHOUSE_CLOUD_KEY_SECRET`, or a combined var, per what any-sdk expresses).
- **`$.result` envelope everywhere** - every response wraps its payload as `{"result": ..., "requestId": ..., "status": ...}`. List operations set `stackql_object_key` to `$.result`. Uniform - flag any deviation found in the inventory.
- **No pagination expected** - responses appear complete (organizations and their children are bounded sets). Confirm across list endpoints in phase 1 and record the confirmation; do not assume silently.
- **Rate limit as a design input** - 10 requests per 10-second window per API key. Test suites pace accordingly (serial execution, deliberate delays); docs note the limit and its implication for wide multi-service queries. 429 responses are the signal.
- **Lifecycle via PATCH** - service start/stop is `PATCH .../state` with a `command` body field, and several updates use operation-array semantics (`ipAccessList` PATCH takes `add`/`remove` arrays rather than replacement). Map state changes as `EXEC` (`services.update_state` with `@command`) and document the array-patch semantics plainly on the affected `UPDATE` methods - no attempt to hide the wire shapes.
- **Prometheus endpoints are skipped** - the metrics-scrape endpoints return Prometheus text format, not JSON; skip with a reason code per the standing non-JSON exclusions.
- **Reads and writes** - full lifecycle: service create/scale/delete, key and member management, backup configuration, ClickStack dashboards and alerts as code. FinOps (usage cost by day and entity) and estate inventory lead the documentation.

## Toolchain rules

- Use the **latest** `@stackql/provider-utils` (see [npm](https://www.npmjs.com/package/@stackql/provider-utils)). Check for a newer version before starting work; do not pin to an old minor.
- Node.js >= 20. `type: module` in package.json.
- Wrap the two CLI entry points (`provider-dev-utils.mjs`, `docgen-utils.mjs`) as npm scripts, invoked through `node` (not `.bin` shims). Pass flags with npm's `--` separator.
- A local `stackql` binary is required for testing (`$STACKQL`, `./stackql`, or on `PATH`).

## Build pipeline

Every step is deterministic and re-runnable. Manual mapping decisions are applied as rules in scripts, never hand-edits to CSVs or specs. Validate-and-fail-without-writing is the standard for every script.

### 0. Fetch and pin the spec

`bin/fetch-spec.sh` per the spec-source section. Report the spec's stated version and operation count at every fetch.

### 1. Split into service specs

`npm run split` with `--provider-name clickhouse`. Candidate service split (final decision from the endpoint inventory, recorded in `provider-dev/config/service_names.json`):

`organizations` (organizations, activities, usage cost, prometheus-skips recorded here), `services` (services, state, replicaScaling, password, clickhouseSettings, serviceQueryEndpoint, privateEndpoint, privateEndpointConfig), `backups` (backups, backup configuration), `keys` (API keys), `members` (members, invitations), `network` (org-level private endpoint resources if distinct from service-level), `byoc` (BYOC infrastructure), `clickstack` (dashboards, alerts, sources, webhooks), `postgres` (Managed Postgres services and their metrics endpoints minus prometheus skips)

### 2. Generate mappings

`npm run generate-mappings`, then `node provider-dev/scripts/map_operations.mjs`:

| Operation pattern | StackQL verb | Resource / method |
|---|---|---|
| GET collection | `SELECT` | `<resource>.list`, objectKey `$.result` |
| GET single | `SELECT` | `<resource>.get`, objectKey `$.result` |
| POST create | `INSERT` | `<resource>.create` |
| PATCH update | `UPDATE` | `<resource>.update` - array-operation semantics (ipAccessList add/remove) documented on the method |
| DELETE | `DELETE` | `<resource>.delete` |
| PATCH `.../state` (start/stop command) | `EXEC` | `services.update_state` with `@command` |
| Prometheus text endpoints | skipped | non-JSON, reason-coded |

Resource names are plural snake_case (`services`, `api_keys`, `usage_costs`, `clickstack_dashboards` or service-scoped `dashboards` - inventory decides), consistent with the sibling builds. The script validates: every generator-relevant operation mapped or explicitly skipped with a reason code, method names unique per resource, overloaded SQL verbs have unique required-parameter signatures. Fail without writing on any violation.

### 3. Normalize

`node provider-dev/scripts/pre_normalize.mjs` (ClickHouse-specific adjustments if any surface - expected minimal given the vendor's spec-quality investment), then `npm run normalize -- --api-dir provider-dev/source`. Deep nested objects (ClickStack tile configs, scaling blocks, ipAccessList) lower to JSON-blob columns addressed with `json_extract`.

### 4. Generate the provider

```bash
rm -rf provider-dev/openapi/*
npm run generate-provider -- \
  --provider-name clickhouse \
  --input-dir provider-dev/source \
  --output-dir provider-dev/openapi/src/clickhouse \
  --config-path provider-dev/config/all_services.csv \
  --servers '[{"url": "https://api.clickhouse.cloud"}]' \
  --provider-config '{"auth": {"type": "basic", ...per the jira basic-auth finding...}}' \
  --naive-req-body-translate \
  --overwrite
```

No pagination config pending the phase 1 confirmation. Then `node provider-dev/scripts/post_process.mjs` for anything the generator cannot express, as surfaced by the integration tests - expected minimal.

### 5. Test

Same four layers as the k8s repo, in order:

1. **Offline validation** - local file registry, `SHOW SERVICES/RESOURCES/METHODS`, `DESCRIBE EXTENDED` on representative resources (`clickhouse.services.services`, `clickhouse.organizations.usage_costs`, `clickhouse.keys.api_keys`)
2. **Meta-route tests** - `npm run start-server` / `npm run test-meta-routes -- clickhouse --verbose` / `npm run stop-server`
3. **Integration tests** - `tests/integration/mock_clickhouse_server.mjs` serving real wire shapes (capture from a live org, redact); assert row-level results per archetype: `$.result` unwrapping for both list and single, basic-auth header presence, a full API key `INSERT` / `UPDATE` / `DELETE` lifecycle, the `EXEC` state command, an ipAccessList array-patch `UPDATE`, and a ClickStack dashboard round trip
4. **Smoke tests** - `tests/smoke_test.py` (pystackql) against a real organization: read smokes (org, services, members, usage cost) plus a disposable write lifecycle - an API key and, where the org allows it, a smallest-tier service created, stopped, and deleted within the run (services bill by usage - keep the window minutes, or make the service lifecycle a separately gated job), `stackql-smoke-<stamp>` naming, sweeping breadcrumbs first; serial pacing under the 10-req/10s limit throughout; `--registry public` variant doubles as post-publish verification

A dedicated ClickHouse Cloud organization (trial credits or a standing dev org) is the live test target. Never run tests against a production organization. The rate limit makes test pacing a correctness concern, not a courtesy - build the delay into the harness.

### 6. Publish

Push the `clickhouse` dir to `providers/src` in a feature branch of [`stackql-provider-registry`](https://github.com/stackql/stackql-provider-registry) and follow the registry release flow. Verify with `registry pull clickhouse` against the dev registry.

### 7. Docs microsite

`website/` is Docusaurus 3.10 following the shared architecture: shared `stackql/docusaurus-config` vendored to `.shared-config/` at build time; site-local files limited to `website/provider.js` (`providerName = 'clickhouse'`, `providerTitle = 'ClickHouse Cloud'`), thin config wrappers, shared components, and `static/CNAME` pinning `clickhouse-provider.stackql.io`.

- Author `headerContent1.txt` / `headerContent2.txt` in `provider-dev/docgen/provider-data/` (installation, API key creation in the console with role guidance, the basic-auth connection convention, the rate limit note, the Cloud-only scope and the `clickhouse_server` roadmap note, example queries)
- `npm run generate-docs`, then `node website/scripts/sanitize-docs.mjs`
- Publish via GitHub Pages, DNS: `clickhouse-provider.stackql.io` CNAME -> `stackql.github.io.`

Lead the docs examples with the queries this provider exists for: service estate inventory across organizations (state, tier, provider, region, scaling config), daily usage cost by entity (the FinOps lead), idle-service detection (stopped vs running against cost), API keys by age and permission, member and invitation audit, backup configuration coverage, and ClickStack dashboards/alerts as code. One cross-provider example unioning ClickHouse Cloud services with Snowflake warehouses and Databricks clusters - the data platform estate in one query - is the flagship for the data-theme campaign.

### 8. CI

GitHub Actions: fetch + pin check + build, integration tests against the mock server, meta-route tests, and (secret-gated) the smoke suite against the dev organization with serial pacing. Add a spec-drift job diffing the served spec against the pin - given the vendor's stated evolution posture, this job matters more here than usual. Model on the k8s repo's `build-and-test.yml`.

## Writing conventions

- README and docs copy: measured, precise, no hyperbole. Third-person or passive framing for descriptive copy. The Terraform comparison is expressed through capability statements and runnable examples, never editorializing.
- No em dashes; use `-`. No characters not on a QWERTY keyboard; use `->` for arrows.
- Sample queries follow the k8s README style: realistic, runnable, `json_extract` for nested fields.

## Non-negotiables

1. Latest `@stackql/provider-utils`, always
2. The k8s `feature/provider-dev` repo is the reference pattern; sibling-build NOTES.md findings are reused, not re-derived - deviate only with a documented reason in the README
3. Deterministic scripts, never hand-edits to derived artifacts
4. Every regeneration is followed by the integration test suite before commit
5. Test harnesses pace under the documented rate limit - a 429 in CI is a harness bug
6. Smoke tests clean up everything they create - a failed run must not leave billable services behind
